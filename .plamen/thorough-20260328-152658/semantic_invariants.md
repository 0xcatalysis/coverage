### STEP 2b Results: Recursive Stale-Read Traces

#### SYNC_GAP 1: totalPrincipal lags userPrincipal during withdrawal execution

**Level 0:** `totalPrincipal` is still pre-withdrawal value during the window between `_updateDebtsAfterWithdrawal()` (L552 which updates `userPrincipal[owner_]` to `newPrincipal`) and `totalPrincipal -= userPrincipalForWithdrawal` (L189 of `_withdraw()`).

**Level 1:** Functions that READ `totalPrincipal` during this window:
- `evaluate()` (L384): reads `PENDING_CLAIM_AMOUNT_SLOT` — does NOT read `totalPrincipal`. Safe.
- `_isPolicyActive()` (L153): reads `policyId` — does NOT read `totalPrincipal`. Safe.
- `_accruedPremiumFor()` (L97): reads `totalPrincipal` — would compute slightly wrong accrued premium using stale totalPrincipal. BUT: `_accruePremium()` is called at the START of `_withdraw()` (L174) before any state changes. The evaluate() call is a view function called during the claim filing in `_settleWithdrawalTransfer`. `_accruedPremiumFor()` is not called from `evaluate()`. Safe.
- `totalAssets()` (L108): reads `totalPremiumLiability` and `_accruedPremiumFor(mv)` → `totalPrincipal`. If `totalAssets()` were called during the window (e.g., by an external observer or integration), it would return a slightly high value (totalPrincipal used for premium calculation is stale high). But `totalAssets()` is external/view, not called internally during the withdrawal callback chain. Safe.

**Level 2:** No Level 1 functions are called during the window that cascade to Level 2 issues. The `evaluate()` callback from ClaimManager does not use `totalPrincipal`.

**Level 3 (Terminal impact):** TRANSIENT inconsistency. No permanent state corruption possible because `totalPrincipal` is decremented unconditionally at L189 which always executes after `_executeWithdrawal()` returns (function call stack is linear). The stale window is bounded by the execution of `_settleWithdrawalTransfer` + `_claimInsurance` in `_executeWithdrawal`. **Impact: Reversible. Only affects on-the-fly view calls during the tx, not persistent storage.**

**Attacker escalation:** An attacker cannot force the worst-case: re-entrance is blocked by `nonReentrant` (transient storage). The callback via `evaluate()` is a view-only call and does not read `totalPrincipal`. Cannot be weaponized.

**Conclusion:** Level 0-3 trace confirms this is a benign transient inconsistency. Matches PC1-3 (Informational, already in inventory).

#### SYNC_GAP 2: totalPremiumLiability phantom liability after deep-loss withdrawal

**Level 0:** After a deep-loss withdrawal where `assetsReceived < uncappedPremium`, `totalPremiumLiability` is decremented only by `premiumForWithdrawal = assetsReceived` (L583), NOT by `uncappedPremium`. The delta `uncappedPremium - assetsReceived` (forgiven premium) remains in `totalPremiumLiability`.

**Level 1:** Functions that READ `totalPremiumLiability` and compute incorrectly with the inflated value:
- `totalAssets()` (L108): `totalLiability = totalPremiumLiability + _accruedPremiumFor(mv)`. Inflated `totalPremiumLiability` → deflated `totalAssets()` → deflated share price for remaining depositors. Remaining users see fewer assets per share than they should.
- `_liabilityHeadroom()` (L162): `morphoVal - totalPremiumLiability`. Inflated liability → reduced headroom → **`_accruePremium()` accrues LESS premium in future intervals** because the cap is lower. This is actually the PROTECTIVE behavior: fewer assets available → less premium accrual capacity. Net effect: a subsequent depositor entering post-deep-loss will see a (correctly) depressed share price and an under-counted `totalAssets()`.
- `userShortfall()` (L427): uses `totalPremiumLiability` via `totalAssets()` path. Inflated liability → higher apparent shortfall → remaining users' shortfall appears larger → they may get higher insurance payouts on their own subsequent withdrawals.

**Level 2:** The inflated `totalPremiumLiability` affects share price calculation for all subsequent depositors. New depositors get slightly MORE shares for the same assets (deflated NAV). On their future withdrawal, they redeem proportionally more Morpho assets than they put in (at the expense of the deep-loss surplus).

**Level 3 (Terminal impact):** Persistent state corruption for as long as no user withdraws to "clear" the phantom liability. The only way the phantom liability is cleared: if a subsequent user withdraws and `premiumForWithdrawal` eventually consumes the phantom excess (but this won't happen — the phantom amount represents forgiven premium that was never paid, so no future withdrawal will reduce `totalPremiumLiability` by the phantom delta unless another user's owed premium exceeds their withdrawal proceeds). **Impact: PERMANENT for that increment of totalPremiumLiability. Deflates totalAssets() → depresses share price for all remaining holders.**

**Attacker escalation:** An attacker could deliberately withdraw at maximum loss (trigger deep-loss scenario) to maximize the phantom inflation in `totalPremiumLiability`, depressing share price for remaining depositors. This requires significant Morpho losses (not attacker-controllable). Not directly weaponizable without an external loss event.

**Conclusion:** This is the CS-2 finding (already confirmed Medium in inventory). Level 3 trace confirms PERMANENT state corruption (not transient), inflating `totalPremiumLiability` and depressing `totalAssets()` and share price for remaining holders. Severity remains Medium.

#### SYNC_GAP 3: sum(userMorphoShares) dust drift above actual Morpho balance

**Level 0:** After many partial withdrawals with Floor rounding, `sum(userMorphoShares[u])` may accumulate a small positive dust above `IVaultV2(morphoVault).balanceOf(address(this))`. The cap in `_executeWithdrawal()` L542-544 only applies at final withdrawal (when `shares_ == ownerBalance_`).

**Level 1:** Functions that READ `userMorphoShares` and compute incorrectly:
- `_executeWithdrawal()` L537: `redeemShares = userMorphoShares[owner_].mulDiv(shares_, ownerBalance_, Floor)`. If the user does a PARTIAL withdrawal (not final), `redeemShares` is computed from `userMorphoShares[owner_]` which may be slightly high due to accumulated dust from previous partial withdrawals across all users inflating the tracked total. But individual `userMorphoShares[owner_]` is only updated on that user's own withdrawals, so dust from OTHER users does not inflate this user's balance.
- `_userMorphoValue()` (L489): Uses `userMorphoShares[user]` directly to call `convertToAssets(shares)`. If `userMorphoShares[user]` > actual Morpho shares attributable to this user, the fallback `try IVaultV2(morphoVault).convertToAssets(shares)` would compute a value using shares that don't exist — but this returns a value, not an error, since `convertToAssets` just does arithmetic.

**Level 2:** `_userMorphoValue()` is called from `userShortfall()` (L433) to compute per-user shortfall. Slightly inflated `userMorphoShares[user]` → slightly inflated `userMorphoNet` → slightly LOWER reported shortfall → user may not claim full insurance at the margin.

**Level 3 (Terminal impact):** The last user to withdraw will trigger the cap at L542-544 which clears the dust. Before that, the effect is a minor understatement of per-user shortfall via `userShortfall()`. Not material. **Impact: Transient (cleared at final withdrawal). Affects shortfall view function only. No fund loss.**

**Conclusion:** Already documented in Pass 1 and the ACCUMULATION_EXPOSURE/SYNC_GAP flags. Level 3 trace confirms TRANSIENT. No new finding.

#### SYNC_GAP 4: lastKnownMorphoValue not refreshed on gate deactivation

**Level 0:** `setMorphoGateActive(false)` extends `gateGracePeriod` and resets `gateActivatedAt` but does NOT update `lastKnownMorphoValue`. Value remains at the cache written during gate activation (or the last `_accruePremium()` call before the gate was activated).

**Level 1:** Functions that READ `lastKnownMorphoValue` and compute incorrectly:
- `_morphoValue()` (L139-147): Returns `lastKnownMorphoValue` ONLY when `convertToAssets` reverts. If the gate was lifted but Morpho is still returning incorrect values (temporarily), the stale cached value flows into:
  - `totalAssets()` → share price computation
  - `_liabilityHeadroom()` → premium accrual cap
  - `_accruePremium()` → the `morphoValue` used for the first post-gate accrual
- If `convertToAssets` works fine post-gate-deactivation (common case), `lastKnownMorphoValue` is ignored and fresh value is used. In this case no stale-read occurs.

**Level 2:** If stale `lastKnownMorphoValue` is used (only when `convertToAssets` still reverts post-deactivation):
- Stale HIGH value (Morpho lost assets during gate) → `_liabilityHeadroom()` is artificially high → `_accruePremium()` can accrue MORE premium than justified → `totalPremiumLiability` grows faster than the actual Morpho backing supports → NAV underestimated.
- Stale LOW value (Morpho gained yield during gate) → opposite effect, less premium accrual allowed post-gate.

**Level 3 (Terminal impact):** If `convertToAssets` continues to revert after gate deactivation (edge case — gate lifted but Morpho still broken), premium is over-accrued against stale high value. First user to withdraw post-gate with premium owed may receive fewer assets than expected. **Impact: Conditional on Morpho still being broken post-gate. Limited duration (next successful redeem updates cache). TRANSIENT once Morpho recovers.**

**Conclusion:** Already captured by CS-3 (Stale lastKnownMorphoValue During Gate, Low severity). Level 3 trace confirms TRANSIENT/CONDITIONAL impact.

#### SYNC_GAP 5: _claimApprovalRequired and premiumDefaulted silent 0 returns

**Level 0:** When `_claimApprovalRequired[policyId] == true`, `fileClaim()` reverts. The wrapper's try/catch (L365-372) catches this revert and returns 0 payout silently.

**Level 1:** The try/catch absorption means `_claimInsurance()` returns 0. The withdrawal proceeds:
- `_settleWithdrawalTransfer()` computes `totalOut_ = netAssetsReceived + 0` (no insurance payout)
- User receives only Morpho proceeds minus premium, without insurance
- `pendingPremium += premiumForWithdrawal` — premium is still collected
- `totalPremiumLiability -= premiumForWithdrawal` — liability decremented correctly
- All state accounting is correct

**Level 2:** The user who triggered the first successful claim set `_claimApprovalRequired = true`. Curator must call `approveNextClaim()` to clear it. Until cleared, ALL subsequent withdrawers who have losses will get 0 insurance payout. They don't know this ahead of time from the contract interface.

**Level 3 (Terminal impact):** Users suffering losses during the `_claimApprovalRequired == true` window receive $0 insurance payout without any warning. State accounting is correct (premium collected, no claim filed). **Impact: Loss of insurance payout for ALL users during the approval-pending window. Not reversible for those users once they've withdrawn.**

**New SYNC_GAP P2-1 flagged:** The `evaluate()` callback (L384-403) is only reached when `fileClaim()` SUCCEEDS (i.e., `_claimApprovalRequired == false`). There is NO scenario where `evaluate()` is called and then `_claimApprovalRequired` state matters during that same call — the gate is checked before `evaluate()` is called in ClaimManager. However:

**Level 1b — NEW observation:** When `_claimApprovalRequired == true`, the wrapper calls `fileClaim()`, which reverts. `PENDING_CLAIM_AMOUNT_SLOT` was already written (L355) before the `try` block. After catch, L369 clears `PENDING_CLAIM_AMOUNT_SLOT` back to 0. This is correct — the transient slot is cleaned up. No stale transient state.

**Conclusion:** The Level 3 impact is already captured by AC-3 (Claim Approval Gate Allows Curator to Permanently Block Multi-Claim Policies, Medium). No new finding.

And `pendingPremium += 0` and `totalPremiumLiability -= 0`. The user receives `netAssetsReceived = 0 - 0 = 0` from Morpho and gets insurance payout (if any) as `totalOut_`. Insurance is computed on `insuredBasis = userPrincipalForWithdrawal - 0 = userPrincipalForWithdrawal`. This is correct — a user with no Morpho shares gets their full principal as the loss basis.

**But wait:** `redeemShares == 0` can occur when `userMorphoShares[owner_] == 0` (the mulDiv at L537 produces 0) or when the mulDiv rounds down to 0 for a tiny partial withdrawal. In the latter case, `userPremiumDebt[owner_]` is updated via `_updateDebtsAfterWithdrawal()` (called unconditionally at L552), so premium debt is checkpointed even when no Morpho shares were redeemed. This means a user could extract insurance without the premium being collected (since `premiumForWithdrawal = 0` when `assetsReceived = 0`). However, `_computeInsurance` (L317) requires `insuredBasis > netAssetsReceived` — when `netAssetsReceived = 0` and `insuredBasis = userPrincipalForWithdrawal > 0`, this condition is satisfied only if there IS an actual loss (principal > net). This is correct behavior for a total-loss scenario.

**NEW SYNC_GAP P2-C2c:** `totalPremiumLiability` is NOT decremented when `redeemShares == 0 && uncappedPremium > 0`. When a user has 0 Morpho shares but non-zero `userPrincipal` (abnormal but theoretically possible via dust), they owe premium (`uncappedPremium > 0`) but `premiumForWithdrawal = min(uncappedPremium, assetsReceived=0) = 0`. So `totalPremiumLiability` retains the phantom liability for this user's premium. This parallels the deep-loss SYNC_GAP (CS-2) but for a different trigger (0 Morpho shares vs insufficient assets). In normal operation `userMorphoShares[user] > 0` when `userPrincipal[user] > 0`, so this is an edge case (requires state corruption first). **Mark as CONDITIONAL — requires `userMorphoShares[user] == 0 && userPrincipal[user] > 0` precondition.**
